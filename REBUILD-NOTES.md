# Rebuild notes for the CodeBuddy build

Generated the morning after the bake-off by an eight-agent read-only review (two lenses per target: rebuild architecture, code quality). Nothing here was applied to the code; it is analysis for whichever game the team picks. Read your chosen game's section, skim foundation, ignore the rest.

## Memory Garden

Architecture verdict: This is the best-architected of an overnight prototype set I would expect to be held together with tape, and the reason is that the seams are cut in the right places rather than in convenient places. Three of them carry real weight: aiGenerate is one function with one signature and a source label, so swapping in Tencent's model touches no call site; composePlant is pure, DOM-free and deterministic from the answer tuple, so it runs under plain node for the contact sheet, storage holds answers instead of pixels, and the trait mapping is four small tables anyone can read; storage validates on read with an id allowlist and never throws. Around those, the small decisions are unusually well-judged for one night of work: sentence-form phrases living with the data, pre-worded counts, aria-disabled instead of disabled with a kind nudge, a stale-tap guard keyed to view change rather than a blanket debounce, a lint that proves it can fail before it is trusted. The weakness is proportion. Something like 900 of roughly 2300 lines of game code is hand-rolled SVG geometry in composer.js and data.js, and essentially all of it dies the day real art arrives, taking with it the viewBox-clipping problems that needed a 40-combination test to police. The view machine leaks a fifth state, the draft is module-global and reset in two places, and loop.mjs is 1431 lines of excellent tests in one indefensible file. So: roughly two thirds of the thinking survives a rebuild and only about a third of the literal code does, and the surviving code is the quiet infrastructure rather than the visible game. That is the right way round. Hand a CodeBuddy session shared/ai.js, shared/storage.js, tokens.css, the four composer trait tables, the guard constants, and the QA harness patterns, and the two weeks go into content, art and polish instead of rediscovering that a disabled button at 55% opacity is a trap for an 80 year old.

Code health: Genuinely well-built for an overnight prototype (clean delegation, no listener leaks, deterministic composer, unusually thoughtful comments), but almost every serious defect sits on the assumption that the AI seam resolves instantly and localStorage never fails, which is exactly what the CodeBuddy rebuild will break first.

### Keep (carry into the rebuild)

- The aiGenerate seam, verbatim. `shared/ai.js:87` is `aiGenerate({game, event, context}) -> Promise<{text, meta}>`, already async, already returning a promise, with `meta.source` labelling every line 'bank' or 'fallback' and reserving 'llm'. Every call site in memory-garden already awaits it (main.js:74, 233, 301, 361, 439). Wiring Tencent's model into the rebuild is one function body, zero call-site edits, and the JSON bank becomes the offline fallback on the catch path. Nothing else in the repo buys this much for this little.
- The composer trait table shape, verbatim, even if every pixel of the drawing gets thrown away. `js/composer.js:35-98` declares four independent lookup tables (SPECIES_BY_OBJECT, PALETTES, BLOOMS, ORNAMENTS) plus a FALLBACK entry per axis, and `composePlant` guards each axis against garbage before touching it (composer.js:731-734). Four axes, one table each, one fallback each. Real art from Miora slots into exactly these keys. This is the design that makes 8 objects x 5 x 5 x 5 = 1000 combinations tractable for two people in two weeks.
- Determinism from the answer tuple, not from stored output. `seed = hashString(objectId|who|where|feeling)` (composer.js:736) feeding one mulberry32 rng, with every jitter drawn from that rng only. Consequence: storage holds answers, not SVG (main.js:344-359), a saved plant regrows byte-identical, and the state schema stays small enough to migrate. The QA proves it at loop.mjs:559-581. Carry this rule into the rebuild before anyone is tempted to cache rendered art in localStorage.
- data-* trait attributes on the composed SVG root (composer.js:765-770: data-species, data-palette, data-bloom, data-ornament, data-seed). Costs five string concatenations and turns 'do two plants actually look different' into a one-line DOM assertion (loop.mjs:251-268, 440-446). Whatever the rebuild renders with, stamp the traits onto the rendered node. Highest test-leverage-per-byte in the whole codebase.
- The `phrase` field on every object and every option (data.js:111, 171-198), separate from the display `label`. Sentence form lives with the data, so no template ever has to guess an article, and `phraseFor` (main.js:138-141) is pure lookup. Same trick on the count: main.js:233-235 hands the bank a pre-worded 'one memory' / '2 memories' so no template can ever render '1 memories'. Both kill an entire bug class at the data layer instead of patching it in prose.
- The stale-tap guard and its keyboard exemption. `STALE_TAP_MS = 350` (main.js:22), timestamped on view change only (markViewShown, main.js:158-163), and `staleTap` returns false for `event.detail === 0` so a key press is never swallowed (main.js:169-174). It swallows the second half of a double tap aimed at the previous screen, and because it keys on view change rather than a global debounce, answering three chips fast is never punished. That distinction is the whole insight and it is easy to lose in a rewrite.
- Reentrancy flag plus the id recipe on the async write. `growing` (main.js:39, 336-374) guards the await inside growPlant, and ids are time + seed + random (main.js:347) so two identical memories planted in the same millisecond still get different ids. QA drives three synchronous clicks and asserts one plant (loop.mjs:1241-1269). Any rebuild where grow crosses a network call to a real LLM needs this on day one, not after the demo.
- Validate-on-read storage with an id allowlist. `isPlant` + `PLANT_ID_PATTERN = /^[A-Za-z0-9_-]{1,64}$/` + a filter on load (main.js:25, 83-99), and plot buttons built with createElement/dataset rather than string concatenation (main.js:194-214, with the reasoning in the comment above it). loop.mjs:1194-1239 feeds it a real `"><img src=x onerror=alert(9)>` id and asserts no dialog, no img node, good plant survives. Cheap, and it is the difference between a demo and something you would let a judge type into.
- The 'not yet' button pattern. aria-disabled instead of disabled, opacity 1, pointer-events auto, answering the tap with a kind line rather than silence (main.js:273-290, garden.css:170-181). The subtle part is the CSS note: both resting states pass contrast, the 140ms crossfade between them does not, so the transition is pinned to transform only. That is pinned by a test at loop.mjs:856-860. Nobody rediscovers this in a two week build.
- QA patterns, four of them. (1) `press(target, selector, expect)` asserts what the tap caused and counts retries, so a guard that starts eating real taps surfaces as a number (loop.mjs:105-120, asserted at 1398-1401). (2) Tap count as a first-class definition-of-done metric, not a comment: 'a chips only loop stays at 9 taps or fewer' (loop.mjs:359). (3) One fresh browser context per adversarial scenario (freshPage, loop.mjs:285-290) so no test can quietly change what an earlier one measured. (4) lint-bank.mjs proves its own rules before trusting them: SELF_TEST at lint-bank.mjs:96-106 feeds nine synthetic broken lines through and fails if the lint does not catch them.
- The contact sheet rendering at real plot size. contact-sheet.mjs:34-38 plus rows 5 and 6 re-render the same eight species at 100px, the size a garden plot actually gives them, with the note that distinctness surviving only on the ceremony stage is not distinctness. A judging artefact a human can scan in ten seconds, generated by node with no browser. Regenerate it every time the art changes.
- Caption written once at grow time and stored, replay narration generated fresh on every open (main.js:361-362 vs main.js:439). The story never drifts under the player, but reopening still feels alive. One line of policy, and it is the right one.
- tokens.css with no type step below 28px and the contrast ratio written next to every colour pairing. The floor is enforced by absence: a 14px value does not exist to be typed. Port the file as-is; it is already three-game generic and it is the fastest possible answer to a judge asking about senior accessibility.

### Redo (redesign rather than port)

- The hand-rolled SVG geometry. composer.js:190-536 is roughly 350 lines of bezier evaluation, blade and frond construction, and per-species anchor tuning, plus another ~180 lines of inline object art in data.js:19-105. It is the largest block in the game and the least reusable once Miora supplies real art. What better looks like: composePlant keeps its signature, its seed, its trait tables and its anchor concept, but becomes layer assembly over named assets. Species body sprite, palette applied as fill tokens, bloom sprite instanced at anchor points, ornament sprite positioned by species anchor. Deletes the entire viewBox-clipping bug class that needed a 40-combination test to catch (loop.mjs:583-649).
- Palette as hardcoded hex inside a JS object (composer.js:61-68), with its contrast notes living in a code comment far from tokens.css where every other contrast note lives. Better: five palette sets as CSS custom properties on the SVG root, keyed by feeling. A designer retheme becomes a CSS edit, the happy-yellow 3.03:1 issue the README already flags gets audited alongside every other colour, and the composer stops carrying colour knowledge it does not need.
- Recomposing every plant on every garden render. renderPlots (main.js:216-227) calls plotButton per plot, which calls composePlant per plot, on every single return to the garden. Six plots is nothing; forty plots after a month of a real senior using it is a visible stall on a cheap Android. Better: memoize by plant.seed, or compose once at grow time and cache the markup. The README already lists this as a known issue, so it is a decision, not an oversight, but it should not survive the rebuild.
- The DOM plumbing: a 26-entry `el` cache built by hand (main.js:627-653) feeding a 120-line bind() of eight anonymous listeners that each open with the same four-line stale-tap preamble (main.js:500-623). It works and it is readable, but it is the part that rots fastest as screens get added, and the guard preamble is copy-pasted eight times. Better in two weeks: one `on(el, handler)` wrapper that applies the guard once, and a per-view render function that owns its own nodes. Not a framework, just one seam.
- The view state machine has a fifth state pretending not to be one. VIEWS (main.js:34-39) holds four sections; the replay overlay is handled outside it with ad hoc calls to markViewShown('replay') at line 435 and markViewShown('garden') at line 447, its own scroll save/restore (gardenScrollY, lines 52, 405, 448), and a hand-rolled focus trap (main.js:455-483). Better: one machine with an explicit state list that includes modal states, and a single transition function that owns focus move, scroll restore, and the stale-tap timestamp. If the rebuild target supports the native dialog element, the 29-line focus trap disappears with it.
- The draft as a module-level mutable object (main.js:42) reset in two places (startFlow at 487-493, the object-card handler at 531-535) and read in a third (growPlant at 343-356). The free-text clearing in particular is duplicated at main.js:491 and main.js:535, and the bug where a note followed the player to a different object (regression-tested at loop.mjs:1162-1192) exists precisely because that reset lived in more than one place. Better: one resetDraft(), or pass the draft as a value into the grow transition so there is nothing module-level to forget to clear.
- loop.mjs at 1431 lines in one file. The patterns inside are the best QA in the repo, the packaging is not: happy-path definition-of-done, viewport sweeps, reduced motion, and eleven fix-round regressions all share one scope, one results array, and one 60-line main(). Adding one regression means scrolling past 1200 lines. Better: a shared harness module (server spawn, watch, press/tap, check, report) plus three or four spec files that import it. Same assertions, same runtime, a coder can find where a new test belongs.
- The content bank as one flat file of event -> string[] (garden-lines.json). Fine for one voice in one language. The real submission is Singapore-facing and the demo value of a Mandarin or dialect pass is high, so shape it as event -> locale -> variants, or one file per locale, before content volume makes the migration painful. Related: `tidy()` in ai.js:200-206 patches punctuation after a missing slot leaves a hole. That runtime repair should not survive, because once aiGenerate is a real model the bank is only the fallback path and can be fully validated at build time. lint-bank.mjs already does exactly that validation. Run it in CI and delete the runtime patch-up.
- Per-game boot constants restated by hand in every game, with absolute paths as string literals: GAME, NS, STATE_VERSION, BANK_URL at main.js:11-14, and BANK_URL is a hardcoded '/games/memory-garden/content/garden-lines.json'. Three games each retyping this is three chances to paste the wrong game id into the wrong bank fetch, and CodeBuddy scaffolding makes that more likely, not less. Better: one tiny game-config module, or read the game id off a data attribute on the html element and derive the rest.
- Dead content in the data layer. Every object carries a `blurb` (data.js:112, 119, 126, ...) that no screen renders, because prose broke the two-column picker at 360px (reasoning at main.js:256-261). Dead-but-maintained-looking data is worse than no data. Either commit to a one-column picker list that has room for the line, which at 360px with 96px art is comfortable, or delete the field. The blurbs are good writing and the picker is the flattest screen in the game, so I would keep them and change the layout.
- The optional free-text field sharing the third prompt screen (index.html:47-58). Two separate bugs trace to that decision: the primary button had to be forced above the note so it stays above the fold (fold test at loop.mjs:1048-1078), and the note-follows-to-a-different-object bug (loop.mjs:1162-1192). Better: give the grandchild note its own step, after the three questions and before the ceremony, with its own skip button. One more tap, two fewer bug classes, and it also gives the note the screen space it deserves as the one thing a grandchild contributes.

### Findings (not applied, ranked)

- [SERIOUS] (games/memory-garden/js/main.js (growPlant, lines 336-378)) growPlant awaits the AI seam before any state change, with no busy state, no catch, and the prompt screen left live: In growPlant the plant object is fully built, then aiGenerate for the caption is awaited, and only after it resolves does the code push, save, swap the stage and call showView('ceremony'). Three things ride on that await being instant, which it is today only because aiGenerate is a synchronous bank lookup wearing an async signature. First, no visual acknowledgement: the player taps 'Grow this memory' and nothing on screen changes until the promise settles, so a two second LLM call reads as a dead button, and the growing flag swallows every retap in silence. Second, there is no catch, only a finally that resets growing, so a rejected call leaves the player parked on question three forever with no feedback and the memory unsaved. Third, nothing locks the prompt view during the await: view-prompt stays visible with live chips and a live Back button, so a player who taps Back while the caption is in flight gets yanked into the ceremony for a memory they were abandoning, and the plant is saved anyway. The QA loop never sees any of this because every run resolves in a microtask. shared/ai.js advertises aiGenerate as the one function a real provider replaces, so this is the exact path the CodeBuddy rebuild touches first.
- [SERIOUS] (games/memory-garden/js/main.js (readGarden lines 93-99, saveState call line 365)) A plant that fails the read filter is silently erased on the next save, and STATE_VERSION is written but never read: readGarden does raw.plants.filter(isPlant) and hands back the survivors. Those dropped entries are not merely hidden for the session: the next successful grow calls saveState with the filtered array, which overwrites storage and destroys them permanently. isPlant is strict (id must match a 1-64 char alphanumeric/dash/underscore pattern, answers must be an object), so any future schema move erases everything on first launch: rename answers, switch to a uuid with colons or dots, nest the object id, and every saved memory is quietly gone. The version field makes this worse by looking like protection that is not there. readGarden ignores raw.version entirely and unconditionally restamps version: STATE_VERSION on the way out, so a payload from any other schema version is accepted, relabelled, filtered and rewritten with no migration hook and no warning. The QA suite does test that a junk entry is dropped and good ones survive, but it never grows a plant afterwards, so it never observes the drop being persisted. For a game whose entire promise is that nothing planted here is ever lost, this is the most damaging defect in the file.
- [SERIOUS] (games/memory-garden/js/main.js (line 365)) saveState failure is ignored, so a failed write shows the player a plant that will not exist after reload: growPlant calls saveState(NS, garden) and discards the boolean it returns. shared/storage.js returns false on a quota exception or when setItem throws (iOS Safari in private browsing is the classic case, and a garden of SVG-bearing plants is not tiny once the count climbs). The plant is already in the in-memory garden.plants array, so the ceremony plays, the garden renders it with the fresh highlight ring, and the player is told in so many words that the soil kept it. Then the tab closes and it is gone with no explanation. Nothing anywhere in the game reads a save result or surfaces a storage problem, and the QA suite runs with healthy storage so it cannot catch this. Either check the return and say something honest, or move to a write-then-read-back confirmation before the ceremony claims success.
- [SERIOUS] (games/memory-garden/js/main.js (line 302)) The prompt heading only accepts generated text when meta.source is 'bank', so wiring the real LLM silently disables the feature: renderPromptHeading writes the static question from data.js, awaits generateFresh, then upgrades the heading only if token === headingToken AND line.meta.source === 'bank' AND the text is non-empty. shared/ai.js documents that meta.source becomes 'llm' once a provider is wired in, keeping 'bank' for the offline fallback. The moment CodeBuddy makes that swap, every generated prompt heading is discarded and all three questions freeze on the hardcoded strings. Nothing throws, no test fails, the screens just quietly stop varying, and the team will be debugging the model call when the bug is a source check written for a two-value world. The stale-token guard immediately above it is the right pattern and should be the only guard here.
- [SERIOUS] (games/memory-garden/js/main.js (renderPlots lines 216-227) and games/memory-garden/js/composer.js) No error boundary anywhere in the render path, and the input that would break it is persisted: renderPlots calls plotButton for each saved plant, which calls composePlant, which reaches into SPECIES_BUILDERS and runs ~800 lines of geometry. A single throw there propagates through renderPlots to renderGarden to start(), leaving the garden div empty with no plants, no empty plots, no message, and the welcome card still saying 'Loading the garden.' Because the offending plant lives in localStorage, a reload reproduces it exactly, so the player has a permanently blank game with no way back short of clearing site data. composer.js has at least two live traps that would do it: stackedBamboo pads its anchor list with anchors[anchors.length - 3], which reads undefined and throws on .x if the per-stalk anchor count is ever tuned down, and three builders divide by (count - 1) with counts that come from an rng, which yields NaN coordinates rather than a throw but produces an invisible plant. composePlant is defensive about its inputs and not at all about its own arithmetic. Wrap the per-plant compose in a try and fall back to the soil mound so one bad memory costs one plot, not the whole garden.
- [MINOR] (games/memory-garden/js/main.js (renderWelcome 229-242, growPlant 376-377, openReplay 439-441)) Async renders other than the prompt heading have no staleness token, so late lines land on the wrong screen: renderPromptHeading correctly guards its late write with headingToken. Nothing else does. renderWelcome is awaited by nobody (renderGarden calls it and moves on), so two quick returns to the garden put two generateFresh promises in flight with the last one to resolve winning, not the last one requested. Same shape at the end of growPlant, where the ceremony line write happens after growing has already been reset in the finally, so a second grow can be underway when the first ceremony line lands. Same in openReplay, where the replay_open line is written after an await with no check that the overlay is still open or still showing the same plant. All three are invisible today for the same reason as finding one: the bank resolves in a microtask. Under a real provider they become visible line-swapping. The token pattern already in the file should be lifted into generateFresh itself so callers cannot forget it.
- [MINOR] (games/memory-garden/js/main.js (line 563)) The gate on growing a memory is a DOM attribute, not the draft model: The prompt-next handler decides whether to nudge or advance by reading el.promptNext.getAttribute('aria-disabled'), while draft.answers[prompt.id] already knows the answer. That makes an accessibility attribute load-bearing game state. If a later edit restyles the button, swaps aria-disabled for the disabled property, or re-renders the button without restoring the attribute, the gate reads as open and growPlant runs with draft.answers.feeling undefined. composePlant then silently falls back to the warm palette, so the player gets a plant in a feeling they never picked, with no error and nothing in the QA suite to catch it since every test answers before pressing. The check should be Boolean(draft.answers[PROMPTS[draft.step].id]) with the attribute kept purely as the announcement of that fact.
- [MINOR] (games/memory-garden/js/main.js (keepFocusInReplay lines 455-483)) The story overlay focus trap leaks on shift+Tab from the heading: keepFocusInReplay collects tabbables with a selector that excludes tabindex="-1", so items is exactly one element, the close button. Focus lands on replay-title on open, which is tabindex="-1" and therefore not in items. On shift+Tab the handler tests active === first (false, first is the close button) and !el.replay.contains(active) (false, the title is inside), so it returns without preventDefault and the browser walks focus backwards out of the dialog into the garden underneath, which is still fully focusable because view-garden is never hidden or inerted while the overlay is up. Forward Tab is trapped correctly, only the backward direction leaks. The QA checks that focus moves into the dialog on open and never tests shift+Tab. Low blast radius on a tap-only phone build, but this is exactly the kind of thing that quietly rots under a rebuild, and adding inert or aria-hidden to main while the dialog is open fixes both this and the screen-reader swipe path.
- [MINOR] (games/memory-garden/js/main.js (lines 603-610) and games/memory-garden/css/garden.css (lines 393-417)) Tapping the empty space below a short story dismisses it, on an overlay that does not look dismissible: The overlay closes when event.target === el.replay, the standard click-outside pattern. On a phone the panel is full width, aligned to flex-start, so the only backdrop region is the strip below the panel, and for a short caption that strip is most of the screen. The overlay is painted with background-color: var(--color-bg), fully opaque and identical to the page background, so nothing signals that the lower half of the screen is a dismiss target rather than more page. A senior resting a thumb low on the phone while reading loses the story with no warning and no undo prompt. Nothing is destroyed (the plant is still there to reopen) which is why this is minor rather than serious, but on a screen whose whole job is unhurried reading it is the wrong default. Either drop the backdrop handler on this overlay or make the panel fill the container so no backdrop is exposed.
- [MINOR] (games/memory-garden/js/main.js (lines 71-75)) generateFresh writes a seed onto the caller's own context object: generateFresh takes the caller's context, assigns merged.seed onto that same reference (there is no copy, merged is the argument when it is non-null), and passes it on. Every current caller hands in a fresh object literal so nothing bites today. It is a one-line landmine for the next person: pass a plant, a config, or any shared object and it silently acquires a seed property that will then be persisted the next time that object is written to storage. Spreading into a new object costs nothing and removes the trap.
- [MINOR] (games/memory-garden/js/main.js (updateMoreCue lines 393-397, listener line 612)) The more-below cue reads layout on every scroll event and never re-measures on resize: updateMoreCue is bound directly to the overlay's scroll event and does three layout reads (scrollHeight, clientHeight, scrollTop) plus a hidden write per event, unthrottled and off any animation frame. On the low-end Android hardware this audience actually holds, that is a forced synchronous layout per scroll tick on the one screen with the most text. It is also never wired to resize or orientationchange, so rotating the phone, or the on-screen keyboard opening and closing, leaves the cue asserting there is more below when there is not, or hiding when there is. A rAF guard plus a resize listener is a handful of lines.
- [MINOR] (games/memory-garden/js/composer.js (lines 208-525)) Eight species builders re-derive the same fan and anchor-padding math with slightly different arithmetic: composer.js is the biggest and most fragile file in the game, and roughly a third of it is the same three ideas written eight times: a fan angle as start + (i / (count - 1)) * sweep, a while (anchors.length < 8) padding loop, and a tips-then-centerOutOrder reorder. The padding loops differ per species in ways that look incidental but are not: ribbonFern pulls from anchors[pad % count] and lerps at 0.72/0.28, wovenPalm does the same at 0.6/0.4, stackedBamboo reaches backwards with anchors[anchors.length - 3]. The magic 8 is a contract with placeBlooms (seven spread blooms plus a first) that lives only in a comment. Any future species, or any tweak to a bloom count, has to rediscover all of it. Three shared helpers (fanAngles, padAnchorsTo, tipAnchors) would cut the file substantially and remove the negative-index and divide-by-zero traps described in the render-boundary finding. Worth doing in the rebuild rather than porting the duplication forward.
- [NIT] (games/memory-garden/js/main.js (line 203) and games/memory-garden/js/composer.js (lines 727-777)) innerHTML safety rests entirely on composePlant's whitelist, with no test asserting the whitelist holds: plotButton, the ceremony stage and the replay plant all assign composePlant output straight to innerHTML. That is safe right now precisely because composePlant validates every one of its four inputs against an allowed-keys table before any of them reaches the SVG string, including the data-palette, data-bloom and data-ornament attributes. The QA suite proves the sibling guard works by feeding in a poisoned plant id, which the PLANT_ID_PATTERN filter catches. Nothing proves the composer's own whitelist holds. The day someone adds a trait carried from stored data (a plant nickname in the aria-label is the obvious one, since the free-text note already exists), this becomes stored XSS with no test failing. A single assertion that composePlant output is unchanged when handed arbitrary garbage in every field would pin it.

## Mahjong Kakis

Architecture verdict: This is the best-engineered of the three prototypes for rebuild purposes, and the parts most worth taking are not the game. The aiGenerate seam, the event__character bank shape, slot-fill with punctuation repair, the seeded RNG, the defensive state adoption, and the whole QA posture (browser-driven suites asserting through data-* hooks, plus a browserless content lint that executes the writing rules) are direction-agnostic and would be the right foundation even if the team picks Memory Garden instead. The game logic itself is thinner than the file count suggests: pair matching is about 40 lines, and a large share of the 694-line game.js and 735-line stylesheet is paying off one decision, making a 16-tile wall fit a 667px phone, which is also the least valuable difficulty lever available. The genuine weak spot is the middle layer. There is no state store, no screen abstraction, and no round persistence, just module-scope singletons and imperative DOM pokes, which is precisely the layer a two-week build with a hub, settings, a bigger cast and family mode will stress first. The saving grace is that the weak layer is small and well-isolated behind clean seams above and below it, so replacing it does not disturb anything worth keeping. Call it 40 percent of the lines surviving and close to 100 percent of the decisions: keep the seam, the bank shape, the memory beat, the hidden dial and the no-timer rule verbatim or near-verbatim, rewrite the screen and state plumbing on day one, and cut table size as the difficulty lever before writing a single line of CSS.

Code health: Unusually disciplined prototype code (event delegation, no listener leaks, defensive state adoption, genuinely thoughtful CSS) with one measured mechanic bug in the adaptive dial and a cluster of timer and async holes that are dormant only because no control currently reaches them, which the CodeBuddy rebuild will change on day one.

### Redo (redesign rather than port)

## Scam Dojo

Architecture verdict: This is the best-architected of the prototypes I would expect from an overnight run, and unusually, the reason is that the seams were placed for the rebuild rather than for the demo. The whole thing is roughly 1,000 lines of game code plus 700 of content plus 2,100 of QA, with a clean three-layer split: shared/ai.js as a single documented swap point, content as data, js/ as boot plus round assembly plus dumb DOM builders. Judged purely on what a two-week build inherits, this is the strongest starting position of the three.

## Foundation (server, shared, QA tooling)

Architecture verdict: The shared foundation is better than it has any right to be for an overnight build, and the reason is that the good parts are constraints rather than conventions. tokens.css has no font size below 28px, so nobody can ship small text by accident. base.css puts hover behind a media query, so nobody can hide information in a state a finger cannot reach. inspect.mjs measures the tap target and text size floor in the browser and exits nonzero, so the floor is a gate and not a memo. aiGenerate never throws and returns a stable promise shape, so the swap to a real model is one function body. Those four things plus the composer trait mapping and the content bank convention are genuinely reusable, and I would carry them into CodeBuddy close to verbatim. What should not survive is everything that exists only because three agents were building in parallel overnight and could not block each other: five hardcoded QA ports, five hand-rolled Playwright runners totalling roughly 5000 lines, two different import path conventions, three per-game stylesheets that each reinvented the shared layer, a package.json with no scripts, and a dev server that cannot hold an API key. Call it sixty percent survivable by value and maybe thirty percent by line count, weighted heavily toward shared/ and the UX decisions rather than the game code. The one real defect I found (context.seed not actually pinning the output) is contained today but sits directly on the path a real model takes, so it is worth fixing in the first week rather than rediscovering in demo week.

Code health: Shared foundation is unusually disciplined for an overnight build (clean AI seam, correct path-traversal defense, contrast math that actually checks out), but four things should be fixed before or during the CodeBuddy rebuild: seeded AI picks are provably non-reproducible, the QA inspector cannot fail on a senior-UX-floor breach, base.css ships a disabled-button rule that breaches the floor the moment anyone uses it, and storage.js has no schema version so three games hand-rolled three different guards.
